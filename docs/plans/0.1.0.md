reviewed adversarially by ChatGPT Sol 6.1 before the maintainer agreed it
(see the end). Progress goes on the issues, never here.

Milestone [0.1.0](https://github.com/londontypescript/primrose-hill/milestone/1):
a local overview of every London TypeScript repo, answering from a cache
fetched fresh with the member's own `gh` sign-in, through a `primrose` CLI

the local server is a target for any website the member visits.

## Order

P0 → P1 → P2 → P3 → P4 → P5

Strictly in order, one subagent at a time: each phase builds on the one
before (P3 queries P2's cache, P4 serves P3's queries), and P1 must land
first so nothing new arrives unchecked. P3's skill and P4's page could
overlap once P3's queries exist, but they share `package.json` and the
query module's interface, so they stay sequential.

## Contracts the briefs must carry

- **Snapshot model (P2):** every record keyed by GitHub's stable node ID, not
  by number or URL, so a transferred issue stays one record. Blocking and
  parent or sub-issue links are separate kinds. Each snapshot has a fetch
  time, the account it belongs to, and a list of what failed.
- **Cache boundary (P2):** the folder is chosen per platform from the user's
  data directory, created with owner-only permissions, and named by GitHub
  host and account; SQLite's journal files live beside it. A test switches
  account and finds nothing from the first.
- **Whole or nothing (P2):** a refresh writes in one transaction. A test
  fails the fetch half-way and finds the previous snapshot unchanged.
- **Unknown is not unblocked (P3):** a goal with no recorded blockers is
  shown as "no recorded blockers", and the count of open issues without any
  recorded link sits beside it. Cycles are reported, never followed forever.
- **The CLI is the interface (P3):** the skill and the dashboard read
  nothing the CLI's queries don't expose; JSON output carries a schema
  version, and its shape has a test.
- **Every security rule has a test that fails without it (P4):** Host and
  Origin checks, the token, cross-site rejection, the Content Security
  Policy, and issue text rendered as text.

## How each phase runs

1. The orchestrator writes the brief: the issue, the contracts above, the
   files the subagent may and may not touch, done-when. Delicate briefs (P2,
   P4) get an adversarial ChatGPT Sol 6.1 review first, then a short
   re-check once its findings are folded in.
2. The subagent works in its own worktree and branch from the latest
   `main`, test-first, and commits only. Shared files (`package.json`, the
   lockfile, `tsconfig*.json`, `vite.config.ts`, the lint config) are the
   orchestrator's. Its handoff report: resolved, deliberately deferred,
   needs a decision.
3. The orchestrator reads every line, lists what the change must defend
   against and checks each, with ChatGPT Sol 6.1's independent review
   (effort high), then one combined pass.
4. `pnpm gate`; the built CLI and the built dashboard, not the dev server;
   a security check of the change; `temple-bar ready`; push once.
5. CI, the maintainer's yes, `temple-bar merge` (or the maintainer's admin
   merge for P1).

**Sessions:** at each merge the orchestrator checks its context. If it's
heavy, it writes the state on the next phase's issue and the maintainer
starts a fresh session.

## Review record

ChatGPT Sol 6.1, adversarial, effort medium, on the design before it went to
the maintainer. Accepted and folded in: the cache outside the clone, per
account, with lost access hiding data at once; refresh as one transaction;
blocking kept apart from parent and sub-issue links; unknown never shown as
unblocked, and "critical path" dropped since there are no time estimates;
one launch command and a versioned JSON contract; gate coverage for the new
folders before any code; the skill checked from fresh sessions in both
agents; the local server's rules (Host and Origin checks, a header token,
strict CSP, nothing external, text never as HTML); AI deferred to 0.2.0 and
gated on a proven runner, with a data notice. Rejected: its incremental-sync
safeguards (per-resource checkpoints, overlapping windows, ETag rules), since
a full fetch of the open state takes 6.7 seconds at this size; and separate
packages per part, since one package keeps one gate.
